# МАЙБАЙК — контекст проекта

Claude Code читает этот файл в начале каждой сессии. Он описывает реальный
стек и правила; спорные решения — с причиной, чтобы их не переигрывали.
Как устроен код и куда класть правку — [CODE.md](CODE.md): слои, путь
клиента через функции, база, деньги, панель, фон, тесты и порядок правок.

## 1. Бизнес

Прокат электровелосипедов курьерам доставки. Казань, две точки: Павлюхина
и Адоратского. Клиент — курьер Яндекс.Еды / Самоката / СберМаркета, берёт
велосипед понедельно с оплатой вперёд. Парк ~190 шт, из них ~25 потеряны,
операционный парк ~165. Средняя аренда ~3 недели, ~65 % выручки — продления.

Второе направление — сторонний ремонт электротехники (велосипеды, самокаты,
трициклы, АКБ). Учёт ремонта своего парка по узлам есть; заказы внешних
клиентов — наряды с плательщиком «клиент» (раздел «Сервис»). Их выручка
живёт на наряде и в `crm.ledger` не попадает: журнал — это аренда.

## 2. Три числа, ради которых существует система

```
Доход/день ≈ N × (1 − %простоя) × средний_чек
```

- **N** — операционный парк
- **% простоя** — цель < 10 %
- **средний чек** — цель 500 ₽/день на велосипед в аренде

Любая фича оценивается вопросом: помогает ли увидеть или сдвинуть одно из
трёх чисел. Бенчмарк конкурента (Саратов, парк 174): загрузка 75 %,
чек 594 ₽/день. Панель считает три числа на сводке и в отчётах,
определения — в CRM.md, раздел «Три числа парка». Не выдумывать свои.

| Метрика | Формула |
|---|---|
| Операционный парк | статусы `available`, `rented`, `repair`, `maintenance`, `reserved` |
| % простоя | велосипеде-дни в `available`+`reserved`+`repair`+`maintenance` ÷ дни операционного парка |
| Средний чек/день | платежи клиентов за период ÷ велосипеде-дни в `rented` |
| Цена аренды | тариф модели (`tariffs.model`); тариф без модели — запасной |
| Арендная выручка | все платежи в `crm.ledger` (kind `payment`). Ремонт чужой техники сюда не входит |
| Долг клиента | отрицательный баланс журнала: периоды начисляются вперёд целиком, не по дням |
| Амортизация | рама (цена − остаточная) ÷ срок службы + АКБ по своей цене и сроку, помесячно |

`lost`, `sold`, `written_off` в знаменатель простоя не попадают никогда.

## 3. Стек (как есть)

- **PostgreSQL 16** — единственный источник истины; схемы `bot` и `crm`.
- **Telegram-бот** (aiogram 3): регистрация, договор и акты, кабинет клиента,
  формы оператора ответом на карточки в служебных чатах. Есть зеркало для MAX.
- **Веб-панель** (FastAPI + Jinja2, сервис `crm`): клиенты, аренды, парк,
  заявки, финансы, отчёты, импорт таблицы. Никакого NocoDB: экраны уже есть.
- **Docker Compose** на VPS в РФ (152-ФЗ): postgres, bot, crm, backup,
  caddy (профиль https), bot-max (профиль max). Бэкап раз в сутки в `./backups`
  и, если задан бакет, зашифрованной копией в S3 в России (`backup.sh`,
  rclone crypt, ключ `secrets/backup_key` - хранится и вне сервера); раз в
  неделю копия разворачивается в одноразовую базу и сверяется с живой.
  У `crm` предел памяти 1 ГБ (замер: пик импорта xlsx ~670 МБ, поэтому
  импорт в панели по одному), у базы и бота предела нет. Обновление —
  `bash update.sh архив.zip`: сперва дамп и прежний код в
  `backups/pre-update-…` (не снялся — стоп), `.env`, `secrets/`,
  `app/*.docx` и `backups/` не трогаются, в конце — как откатиться.
  `deploy.ps1` серверные docx тоже не заменяет, только досылает новые.
  postgres-demo + crm-demo (профиль demo) — демо-стенд для франшизы на
  вымышленных данных: своя изолированная база и своя сеть, ни одного
  боевого секрета и тома, бот не подключается никогда (логин публичен,
  152-ФЗ). На нём же обучение новичков (`app/crm/learning.py`): личный
  учебный вход и шаги администратора точки и мастера, засчитанные по
  записям в базе. В боевой базе учебного режима нет намеренно - учебную
  строку пришлось бы вычитать из каждого отчёта.
- Интеграции: **StarLine** (трекеры) и **Точка Банк** (выписка, чек 54-ФЗ
  в ссылке на оплату) живут внутри — без них раздел «Карта» пуст, а
  выписка не приходит. Сообщения Авито тоже внутри: опрос API ботом,
  ответ из «Входящих». WhatsApp и n8n входят одной точкой — `/hook/inbox`
  с токеном; шлюз WhatsApp внутрь не тянем: Wazzup снаружи, бот только
  отправляет через его API ответы из панели. Телефония — вне системы.
  Рабочая группа точек (фиксация, замена, сдача, долг, GPS, итоги дня)
  переехала из n8n в бота: он сверяет формы с базой, Google-таблицы нет.

## 4. Модель данных (схема `crm`)

`staff`, `access_profiles`, `tariffs`, `bikes`, `bike_status_log`,
`bike_location_log`, `bike_log`,
`repair_nodes`, `repair_items`, `work_types`, `work_orders`, `work_order_items`,
`stock_takes`, `stock_take_items`, `referrals`, `settings`, `suppliers`,
`parts`, `part_docs`, `part_moves`, `part_orders`, `part_order_items`,
`purchases`, `locations`, `bike_models`, `battery_models`, `compat`,
`batteries`, `battery_status_log`, `trackers`, `tracker_positions`,
`tracker_alerts`, `cash_shifts`, `cash_moves`, `bank_txns`,
`message_templates`, `campaigns`, `campaign_sends`, `sign_requests`,
`sign_events`, `pay_orders`, `card_tokens`, `notices`, `notice_log`,
`bonuses`, `doc_templates`, `company_marks`, `saved_views`,
`inbox_threads`, `inbox_messages`, `clients`, `rentals`, `rental_intent_log`,
`rental_bikes`, `rental_extras`, `ledger`, `payment_claims`, `ops_reports`,
`franchisees`, `franchise_snapshots`, `franchise_months`, `feedback`,
`return_photos`, `deals`, `deal_log`, `tasks`, `staff_plans`, `cash_plan`,
`rental_changes`.

- **`bike_status_log` — самая важная таблица.** Пишется триггером
  `crm.log_bike_status` при любой смене `bikes.status` (панель, аренда, бот,
  импорт). Автор — через `set_config('crm.actor', …)` в той же транзакции.
  Пробег (`mileage_km`) снимается тем же триггером со строки велосипеда,
  поэтому пишется одним обновлением со статусом: отдельный апдейт
  записал бы в журнал вчерашнее число. По нему виден накат между
  ремонтами, а не только за аренду.
- **Деньги — одна таблица `ledger`**: платёж (+), начисление/штраф/возврат
  (−), корректировка (±). Баланс = сумма. Колонки «баланс» нет намеренно.
- **Ремонт**: шапка — `bike_log` вида `repair` с общей суммой, позиции —
  `repair_items` с узлом из `repair_nodes`. Свободный ввод узла запрещён.
  **Наряд** (`work_orders`) — процесс вокруг ремонта: кто, на каком этапе,
  за чей счёт. Закрытие наряда пишет тот же `bike_log` + `repair_items`,
  поэтому отчёт «что ломается» о нарядах не знает и не менялся.
- **Сроки ремонта** (`repair_nodes.norm_days`, `settings.repair_norm_days`):
  срок наряда - самый долгий из сроков его строк; строку с узлом без
  своего срока или без узла меряет общий (добавленная работа срок не
  укорачивает), наряд без строк - тоже общий.
  Просрочка - открытый наряд дольше срока, все открытые этапы в счёт
  («ждёт запчасть» - тоже простой); видна на столе сервиса, в нарядах и
  утренней сводкой в чат. Сид узлов срок не трогает. «Срок», а не
  «норма»: норма ремонта в плане месяца - число велосипедов в ремонте.
- **Прайс сервиса** (`work_types`): два листа в одной строке - арендатору
  (`price` + `parts_price`) и стороннему (`price_ext` + `parts_price_ext`),
  цена клиенту = работа + запчасть. Работа листа `null` - «в этом прайсе
  нет», ноль - честный ноль (колодки в рамках ТО). Лист выбирается по
  объекту наряда, не по плательщику: свой велосипед - арендатору, чужая
  техника - стороннему. Пустая цена в строке наряда подставляется из
  листа только когда платит клиент. Прайс владельца (регламент № 11)
  приезжает схемой один раз на версию (`settings.work_price_version`) и
  потом правится в панели; заглушки первого сида, которых не трогали,
  выключаются. Штрафы за экипировку - тоже строки прайса (категория
  «Штрафы и порча имущества»), в журнал клиента они идут видом `fine`
  через пресет, а не нарядом.
- **Пересчёт** (`stock_takes`): ведомость ПРТ снимает ожидаемый парк при
  открытии и не пересчитывает его на лету. Найденный потерянный возвращается
  в парк при закрытии сам (ведомость по точке - на её точку, тем же UPDATE),
  недостача в `lost` — только по галочке оператора.
  `what` - что считаем: всё, велосипеды или аккумуляторы. Отдельной
  ведомости на батареи нет: человек вводит номера подряд, а чей это
  номер, разбирает система.
- **Реквизиты организации** — в `crm.settings` (`company_*`), в документы
  идут подстановками из `app/crm/company.py`. Панель пишет, бот читает
  снимком с коротким TTL: процессы разные, база общая. Там же контакт
  менеджера (`support_contact`): в документы он не идёт, зато подменяет
  зашитый `texts.SUPPORT_CONTACT_URL` на выходе (`company.with_contact`),
  и одна настройка чинит русский текст и восемь переводов разом.
  Поставочные `app/*.docx` реквизитов текстом не несут (ни ФИО, ни ИНН,
  ни авторов в свойствах): арендодатель - только `{{ company_* }}`, и в
  политике ПДн тоже (`contract.fill`). Значения владельца в репозиторий
  не возвращаются даже в тест - проверка по видам. Что в установке не
  настроено, показывает «Готовность» (`app/crm/readiness.py`, только
  владельцу): страница смотрит, о фоновых опросах судит по следам в базе.
  Мастер первого запуска (`app/crm/firstrun.py`, `/setup`) - её же строки
  по шагам: своих проверок и своей записи нет (шаг пишет помощником
  раздела). Встречает только владельца, только установку, застанную
  свежей (ни журнала статусов, ни денег при первой встрече - решение
  пишется в `setup_wizard`, и парк, заведённый потом, мастер не
  выключает), и пока обязательный шаг не пройден: поставочные точки и
  цены «Готовность» принимает, а их надо увидеть. Скрытый не
  возвращается, в демо выключен. Прогресс - `crm.settings`.
- **Закупки** (`purchases`): партия велосипедов одним документом ЗАК;
  единица учёта остаётся велосипедом, амортизация по-прежнему на нём.
  Износ — по сроку службы, не по пробегу. Партия заводится по тем же
  правилам, что и одиночный велосипед: включена сверка — вся партия
  встаёт «на сборке», а не в свободных.
- **Тарифы и «Что купить»** (отчёты, без своих таблиц): срок аренды -
  чек и удержание; платёж - к аренде правилом `_ledger_rentals`, день «в
  аренде» - той выдаче велосипеда, что шла, строка «без аренды» держит
  «Итого» равным сводке. Срок - при выдаче (`issue_period_days` помнит
  его после смены тарифа). Исход (продлили, раньше срока, долг) - только у
  закрытых: у идущей он не известен; признанная потерянной не сдана, и в
  срок и продления не идёт. «Что купить» берёт деньги модели из
  окупаемости, спрос - сутки без свободной и заявки; число - нижняя оценка.
- **План месяца** в `crm.settings` (`plan_rented`, `plan_check`,
  `plan_repair`, `plan_spare`): факт сравнивается с ровным темпом, нормы
  ремонта и подменных - с плитками парка и графиком сервиса. Плитка без
  нормы это просто число. План точки - в строке справочника
  (`locations.plan_rented/plan_check`), не в настройках под её именем:
  переименование его не теряет. Пустой `plan_rented` - общий план не
  задан, и при плане у каждой открытой точки план сети - их сумма;
  заданный руками главнее. Месяц таблицы трёх чисел, который идёт или в
  котором началась история (журнал статусов, у точки - журнал мест),
  помечен «неполный»: формулы те же, но предоплата на пару дней аренды
  раздувает чек. Суточная разбивка (`bikes_in_status_by_day`)
  считает СРЕДНЕЕ за сутки, а не «сколько было в полночь». Прогноз освобождения считается по
  «оплачено до», намерение «продлю» из него исключает аренду.
- **Розыск**: состояние аренды (`rentals.search_at`), а не сущность.
  Пороги в `crm.settings`. Признание потери закрывает аренду и ставит
  `lost` велосипеду И его батареям; долг клиента остаётся в журнале.
  Пометка розыска доезжает до батарей джойном, а не колонкой: статус у
  них всё это время «у клиента», потому что они у него и есть.
- **Оценка риска клиента** (`logic.client_risk`, `db.risk_facts`): чистое
  правило по его же истории - уровень, причины словами и залог по уровню
  из `crm.settings` (`risk_deposit_*`, 0 - не подсказывать). Подсказка, а
  не решение: выдачу не запирает, ничего не пишет, наружу не уходит;
  чёрный список и блокировка запрещают выдачу своим правилом. История -
  закрытая аренда или месяц в аренде; без неё «нет истории», а не низкий
  риск, и минусы новичка идут причинами, пока не наберут средний: иначе
  разовая просрочка давала бы залог меньше, чем у чистого новичка. Стаж -
  дни в арендах, а не календарь с первой. Просрочка - минус на КОНЕЦ
  суток: период начисляется вперёд, минус до вечера в день начисления -
  норма; платёж датирован днём выписки или «Я оплатил», а не зачисления.
  Потеря - первый после выдачи выход велосипеда аренды (по журналу замен)
  из `rented` в `lost`, а не даты аренды: закрытие ставят задним числом.
  Досрочный возврат - против срока при выдаче (`issue_period_days`), а не
  после смены тарифа: так же, как у отчёта «Тарифы».
  Найденный потом велосипед историю клиента не обеляет.
- **Замена велосипеда** (`rental_bikes`): аренда остаётся той же, меняется
  только техника на руках. Журнал перемещений хранит пробег по каждой
  единице отдельно; `bikes.spare` — подменный фонд, не статус.
- **Склад** (`parts`): остаток - сумма `part_moves`, отдельной колонки нет,
  как и колонки баланса у клиента. Запчасть привязана к узлу из
  `repair_nodes`, себестоимость средневзвешенная и правится только
  приходом. Расход в наряд пишет `work_order_items.parts_cost` со склада.
  В `part_moves.cost` лежит себестоимость ЕДИНИЦЫ: деньги движения -
  это `qty * cost`, и отчёты расхода считают именно так.
  `min_stock` - точка заказа: ниже него потребность - нехватка до него,
  ровно на нём («на пределе») - одна штука. «В пути» - строки заказов в
  статусе `ordered`: вычитаются из потребности, иначе сбор заказа задвоил
  бы едущее. Раз в неделю список на исходе уходит в чат (`parts_low`,
  день недели - параметр).
- **Списки** (`logic.sort_rows`, `page_of`, `saved_views`): сортировка
  только по белому списку колонок - имя поля из адреса чужая строка;
  итог в подвале по всему найденному, а не по видимой странице.
  Сохранённый фильтр - строка запроса под именем, своя у сотрудника.
  Выгрузка в xlsx и csv (`_table`); строка с «=» остаётся строкой в
  обоих. Неизвестное расширение - 404, а не «сделаю csv». На телефоне
  список - карточки: класс `cards` у таблицы, `data-label` у каждой
  ячейки. Значок на главный экран - манифест без service worker:
  страницы с ПДн в кэше телефона не оседают.
- **Доход по статьям и платёжный календарь** (`app/crm/cashflow.py`,
  `cash_plan`): статьи - аренда (платежи журнала), сторонний ремонт и
  ремонт арендаторам (оплаченные клиентские наряды - их в журнале нет).
  Календарь ждёт аренду по «оплачено до» и цене периода (не ждёт ручную,
  «сдаю», розыск), плановые строки - то, чего нет фактом; долги - «к
  сбору» отдельно. Остаток вводит человек. В `ledger` ничего не пишет.
- **Расхождения**: парк, аренды и наряды проверяются на несходимость
  (`logic.integrity_issues`) — отчётом в панели и раз в сутки в чат.
- **Сотрудник и Telegram**: `staff.tg_id` ставится самим сотрудником по
  одноразовому коду из панели (`/staff КОД`). Назначенный наряд уходит
  технику сообщением. Панель в Telegram - `/crm`: та же панель как Mini
  App (нужен https-домен), вход логином и паролем в форме панели, а не
  сообщением боту - пароль в переписке остался бы навсегда. Привязанному
  - кнопка «CRM» в меню чата; отвязка и отключение её снимают.
  Быстрые формы в личке (`app/crm/quickforms.py`): `/remont` - сторонний
  ремонт мастера, `/vydacha` - выдача администратора; форма -> предпросмотр
  -> кнопка, запись теми же service-функциями, что панель, права - роль.
  Ответ на карточку наряда дополняет его. Сумма строкой ниже ключа - только
  при пустом ключе (иначе «2500» и «0» склеивались в 25 000).
- **Роли** (`access_profiles`; на экранах - «роль»): Владелец, Администратор,
  Мастер и их «только задачи» - одни слова с обучением, мастером запуска и
  демо. Под именем в меню - название роли (`logic.role_title`), а не старая
  колонка `staff.role`: она знает только admin/manager и мастеру писала
  «Менеджер». Переименование старых «Менеджер»/«Механик» - разово
  (`role_names_v2`) и только нетронутых имён. Логин сотрудника
  необязателен - из ФИО латиницей (`logic.login_from_name`); отказ
  добавления - в том же окне с набранными полями, а не редиректом.
- **Меню** - дерево `app/web/nav.py`, не разметка: права тем же
  `can_view`, горит самый длинный адрес, подпункты разделов (склад,
  сервис, настройки) в колонке, счётчики - правилами страниц, кэш 30 с,
  сбрасывается любой записью. Новый экран - пункт в `NAV`.
- **Мои задачи** (`/my`, `app/crm/mytasks.py`): задачи сотрудника, а не
  сети - наряды по технику, аренды, заявки и тревоги по его точке
  (`staff.location`; без неё - все точки), группа - только с правом на
  раздел, рубли - только с «Финансами». Роли «только задачи» не
  встроенные: схема кладёт их один раз (`task_profiles_seeded`), удалённая
  не возвращается. Без сводки вход ведёт сюда. **Срок доступа**
  (`staff.expires_at`): после него вход не пускает, сессии выбиваются
  тем же стражем, что «активен»; истёкший не отключается - продлевается.
  **Поручения** (`tasks`, `app/crm/tasks.py`, `/tasks`): то, чего в базе
  нет событием. Незакреплённую видит точка и берёт свободный (условие в
  UPDATE); сделал - исполнитель, а не нажавший. Цена задачи - в зарплату,
  ставит и видит её тот, кто ведёт команду.
  **Команда** (`staff_plans`, `app/crm/team.py`, `/team`): план и условия
  оплаты - строка на месяц, месяц без строки живёт по прежней. Факт не
  хранится: выдачи и принятые платежи - по автору записи (staff:<логин>),
  наряды - по технику, задачи - по `done_by`. Зарплата - расчёт, в
  `ledger` не идёт. Рубли - владельцу или с «Финансами».
- **Одно окно**: «Входящие» (`/incoming`, `app/crm/incoming.py`) -
  одна лента сообщений, заявок на аренду и «Я оплатил», один пункт меню
  вместо трёх; это экран, а не таблица: данные и права остаются у своих
  разделов (переписка - только владельцу). Клиенты - сводка за всё время
  с группами (`logic.CLIENT_GROUPS`: действующие, бывшие, ни разу,
  должники, выкупили, сторонний ремонт), плитки по всей базе, а не по
  найденному. «Выкупили» - арендатор, чья последняя аренда проданного
  велосипеда его (покупатель без аренды по-прежнему в amoCRM); вид
  техники ремонта - словами из объекта наряда (`logic.tech_kinds`),
  модель - велосипед последней аренды. Отчёты - сверху
  «Главное» (`logic.report_headline`: период против прошлого такого же,
  `report_prev_span`, и цели), ниже свёрнутые блоки не шире четырёх
  колонок, тем же построителем, что полный отчёт, и только при праве на
  него; всё остальное - в полном отчёте («подробнее», `/reports/months`).
- **Воронка** (`deals`, `deal_log`, `app/crm/deals.py`): «Входящие» доской
  от заявки до сдачи. Сделка - ссылка на обращение, заявку, аренду и
  карточку, а не новая сущность клиента; одна открытая на клиента.
  Этапы ставит сверка при открытии доски, а не крючки в путях выдачи
  (их десяток); время этапа - время события. «В аренде», «Повторное
  продление», «Сдал» ставит только аренда - руками двигаются ранние
  этапы. Имя из канала без карточки - только с правом на переписку;
  ПДн закрытой сделки без карточки стираются через 180 дней.
- **Приглашения** (`referrals`): путь друга от перехода по ссылке до
  первого платежа. Бонус платится и агенту, и другу видом `bonus` — это
  баллы, а не деньги, — и только за клиента, которого не было в базе
  (карточка старого заведена раньше перехода). Оплата счёта за ремонт
  бонуса не приносит: её в журнале нет вовсе.
  Всплеск приглашений у одного агента уходит сигналом в чат, но ничего
  не блокирует.
- **Свои шаблоны** (`doc_templates`, `company_marks`): у вида документа
  всегда включён ровно один шаблон - наш или ваш; выключить оба нельзя.
  Проверка docx идёт до сохранения, а нечитаемый свой шаблон молча
  уступает нашему: без договора клиента оставлять нельзя. Соглашение об
  ЭП файлом не подменяется - его текст хранится в заявке. Подпись и
  печать - png на место подстановки; отпечаток документа считается по
  тексту и от картинки не зависит. Том `doctemplates` общий: панель
  пишет, бот читает снимком.
- **Ввод техники** (`bikes.status = 'new'`, `bikes.checked` jsonb):
  новый велосипед заводится «на сборке» и в операционный парк не входит -
  недособранный в убыток не пишем. Сверка - отметка по каждому полю
  паспорта, на пустом поле не ставится. Снимки сверки на своём томе
  (`bikefiles`): том с ПДн панель читает и не пишет. Смена статуса из
  «на сборке» запрещена - выпускает только кнопка ввода в эксплуатацию.
- **Акции** (`promos`): правило начисления баллов, шесть шаблонов в коде
  (`logic.PROMO_KINDS`), параметры в строке. Скидка считается от цены
  велосипеда (`rentals.base_price`, доп. аккумулятор не в счёт) и
  ложится в `ledger` видом `bonus` в ОДНОЙ транзакции с начислением
  периода (`charge_period(..., bonus=...)`): порознь сбой оставлял бы
  клиента с долгом без пути повторить скидку; предел применений там же,
  под замком строки акции (`for update`), а не по снимку списка. Одна
  на период аренды (частичный уникальный индекс), при двух подходящих
  берётся выгоднейшая; предпросмотр на выдаче и начисление считают по
  одному контексту (`service.promo_context`). На арендах с ручным начислением акций нет. Промокод
  хранится на аренде (`rentals.promo_code`): выдача с датой в будущем
  начисляется дневным проходом, и код обязан дожить до него - поэтому
  проверяется на дату начала. Один живой промокод на слово (индекс по
  `upper(code)`). Уведомление шлёт тот, кто начислил (выдача, кнопка
  «Начислить», дневной проход): повторный проход скидок не видит.
  Сезонная акция ограничивается моделью (по каталогу) и точкой аренды -
  два ключа в `params` (`logic.promo_scope`), не новый шаблон; имя точки
  там переносит каскад переименования. Третий ключ `new_only` - только
  первый период выдачи. Модель на точке простаивает в среднем дольше
  порога (`idle_promo_days`; дни - от позднего из смены статуса и
  переезда) - сводка и страница точки предлагают заполненную форму такой
  акции с `new_only`, но не заводят её: скидка - решение человека, а
  продления идущих аренд простой не снимают. Подменный фонд в простой не
  считается. Шаг 4 выдачи несёт показанную скидку (`logic.promo_stamp`),
  оформление сверяет её с пересчётом по точке, дате и коду из формы.
- **Заявка на аренду** (`bookings`): намерение клиента из кабинета -
  модель, тариф, точка, день. Велосипед под неё НЕ бронируется и статус
  ему не меняется: заявка «на завтра» держала бы простаивающий велосипед
  сутки. Одна открытая на клиента (частичный уникальный индекс), при
  идущей аренде не принимается. Закрывается любой выдачей клиенту, не
  только из «Броней» (`service.open_rental` -> `close_booking`, ссылка на
  аренду), или снятием с причиной, которая уходит клиенту. Диалог в
  боте без состояния: выбор едет в callback следующей кнопки. Точек
  несколько - точка первым шагом, и «свободно N» у модели считается по
  ней, а не по парку.
  Лист ожидания (`app/crm/waitlist.py`): освободилась модель на точке
  заявки - бот зовёт клиента. Событие берётся из журналов статусов и мест
  в круге напоминаний, а не крючками в путях возврата: путей десяток.
  Давние первыми, не больше N на велосипед, заявку - раз в сутки и про
  один велосипед один раз, только днём; счёт - по самим заявкам
  (`waitlist_bike_id`), курсора нет. Заявку, чей день прошёл больше трёх
  суток назад (`WAITLIST_STALE_DAYS`), не зовут: её забыли снять, а место
  в очереди она отняла бы у сегодняшних. «Беру» - отметка и карточка
  команде; велосипед и тут не бронируется, а на сводке такая заявка -
  в горящих «на выдачу сегодня», какой бы день в ней ни стоял.
- **Баллы** (`bonuses`): не деньги, а скидка. В журнале - вид `bonus`,
  никогда не `payment`: платежи формируют средний чек, и бонус завысил
  бы его. Таблица `bonuses` хранит повод («за что»), баланс по-прежнему
  считается по `ledger`. Бонус за отзыв начисляет человек по скриншоту:
  у площадок нет ни API, ни обязанности нам отвечать.
- **Оценка после сдачи** (`feedback`): строку-очередь кладёт
  `service.close_rental` (один на панель и бота) и только когда техника
  вернулась - после потери, выкупа и списания не спрашиваем. Спрашивает
  круг процесса бота (`app/crm/feedback.py`) в Telegram (на языке
  клиента), иначе в MAX, отметкой до отправки, только днём (9–21, окно -
  параметры `feedback_ask`; ночное закрытие ждёт утра); выключенное
  уведомление помечает сдачу неспрошенной - включение накопленное не
  догоняет. Не спрашиваем закрытую в день выдачи (исправление оператора,
  то же правило, что у риска) и сдачу давнее двух суток - и по моменту
  закрытия, и по дате возврата: закрытие задним числом не свежая сдача. Кнопка
  `fb:<аренда>:<оценка>` без подписи: оценку принимает только клиент этой
  аренды в том канале, куда ушёл вопрос, и один раз (`score is null`).
  Комментарий - ответ на просьбу бота (`prompt_msg`), без состояния
  диалога. Низкая (3 и ниже) - сигнал `feedback_low` в чат, один раз, без
  телефона и без слов клиента: они в отчёте «Оценки» (право на клиентов),
  и карточка аренды показывает комментарий только с тем же правом.
  Комментарий - слова клиента, как переписка «Входящих»: 90 дней, потом
  дневной проход его стирает, оценка остаётся. Не шифруется: `INBOX_KEY`
  необязателен. Просьба о нём - с ForceReply, и он скрывает меню: ответ
  бота на комментарий возвращает `main_menu`.
- **Фото при сдаче** (`return_photos`): до шести снимков на аренду, из
  формы закрытия в панели или ответом оператора на карточку сдачи в боте
  (к идущей аренде или закрытой не больше часа назад, `rentals.closed_at`).
  Том `bikefiles` - как у снимков сверки, ПДн там нет; бот монтирует его
  на запись. Имя файла и путь собирает код, путь из базы сверяется с
  шаблоном перед показом и удалением. Отдаёт панель вошедшему с правом на
  аренды; срок `return_photo_days` (180), чистит дневной проход бота.
- **Паспорт АКБ** (`batteries.checked`, `volts`, `amp_hours`): сверка та
  же, что у велосипеда, и настройки те же - «Ввод техники» один на всю
  технику. Напряжение и ёмкость лежат у батареи, а не только в каталоге
  модели: в каталоге паспорт модели, на корпусе табличка экземпляра.
  Статус `new` снимает только ввод в эксплуатацию.
- **АКБ — отдельная сущность** (`crm.batteries`, `crm.battery_status_log`,
  триггер `crm.log_battery_status`): номер на корпусе, статус, циклы,
  журнал. `rented` ставит и снимает только выдача. Счётчик АКБ в карточке
  велосипеда остался для парка без карточек; как только батарея привязана
  к велосипеду, от велосипеда берётся только рама (`frame_amortization`),
  иначе амортизация посчиталась бы дважды.
- **План замены АКБ** (`logic.battery_wear_plan`): дата замены - раньшее
  из «срок службы с карточки от даты покупки» и «ресурс циклов при темпе
  этой батареи» (`battery_models.max_cycles`, иначе
  `settings.battery_max_cycles`). Бюджет 1/3/6 месяцев - по сегодняшней
  цене модели. Амортизацию план не меняет.
- **ПЭП** (`sign_requests`, `sign_events`): заявка на подпись хранит пакет
  документов с их SHA-256 и текст соглашения об ЭП ровно в том виде,
  в каком его приняли. Код подтверждения живёт минуты и в базе лежит
  только хэшем вместе с токеном ссылки. Страница `/sign/<токен>` открыта
  клиенту без входа в панель (в `PUBLIC`), раздел `/signings` — нет.
  Подписанная заявка неизменяема: это протокол, а не карточка.
- **Смета** (`work_orders.estimate_sent_at/approved_at/approved_by/
  declined_at`): смета собирается из строк наряда, а не из поля; клиенту
  уходит перечень работ с кнопками. Статус `approve` - открытый: техника
  разобрана и держит место, руками его не переставить. Отказ закрывает
  наряд отменой. Себестоимость клиенту не показывается. Согласовать
  вживую можно не отправляя смету - сумма всё равно берётся из строк;
  ответ на смету бывает ровно один.
- **Счёт за ремонт** (`pay_orders.work_order_id`): красная линия - его
  оплата в `ledger` НЕ идёт, журнал это аренда. Оплаченный счёт с
  нарядом ставит `work_orders.paid_at` и баланс клиента не трогает.
- **Уведомления** (`notices`, `notice_log`): каталог в коде
  (`logic.NOTICES`), в базе - только правки владельца, поэтому новое
  уведомление появляется в панели без правки схемы. Час есть не у всех:
  событийные уходят в момент события. Выключенное напоминание об аренде
  всё равно помечается отправленным - иначе обратное включение обрушит
  на клиента всё накопленное. История живёт 30 дней и текста сообщения
  не хранит.
- **Бэкап и здоровье сервера** (`crm.settings`: `backup_status`,
  `server_health`): сервис `backup` пишет итог дампа, выгрузки и проверки
  восстановления строкой JSON сам - токена бота у него нет и не нужно.
  Судит и пишет владельцу процесс бота раз в час (уведомление
  `server_health`): беда - сразу, раз в сутки пока длится, «снова в
  порядке» - когда прошла; память между проверками в той же настройке, и
  её отметка - пульс бота для `/healthz/bot`. Упавший бот о себе не
  напишет: это внешний монитор, а не наш код. Облако только шифрованное;
  пустой дамп не вытесняет из облака настоящие копии - судится файл, а не
  живая база (после восстановления последним лежит дамп до него).
- **Счёт на оплату** (`pay_orders`): счёт - намерение, платёж - факт.
  Выставленный счёт в `ledger` не попадает и долг не закрывает; в журнал
  он превращается один раз, когда банк подтвердил оплату или оператор
  принял деньги, и `ledger_id` это фиксирует. Статусы опрашивает процесс
  бота (`app/crm/paying.py`) раз в минуту. Панель ходит в банк только за
  ссылкой и только по кнопке оператора: правило «панель в интернет не
  ходит» про фоновые опросы, а не про один запрос при клиенте.
- **Автосписание** (`card_tokens`): выключено по умолчанию, карта чужая.
  Токен приходит от банка, когда клиент платит по ссылке; номера карты
  не храним. Суточный проход списывает уже начисленный долг и ничего не
  берёт вперёд. Рекуррентные платежи банк включает магазину отдельно -
  до этого отказ банка ложится на счёт текстом как есть. После оплаты по
  ссылке без карты бот раз в 30 дней объясняет привязку - только при
  включённом автосписании и когда банк уже присылал карты: иначе «спишем
  сами» было бы неправдой.
- **Рассылки** (`message_templates`, `campaigns`, `campaign_sends`): шаблон
  хранит текст для Telegram и для MAX отдельно (MAX разметку не понимает),
  подстановки — белым списком (`logic.TEMPLATE_FIELDS`). Кампания собирается
  черновиком и стартует руками. Один получатель — одно сообщение
  (уникальный индекс). Отправляет процесс бота (`app/crm/mailing.py`),
  строку берёт в отправку до неё (queued -> sending): зависшая после
  сбоя или перезапуска - «не доставлено», а не повтор, как у «Входящих».
  MAX-аккаунт попадает в карточку по телефону: мост из MAX-бота
  (`CRM_POSTGRES_DB`) или руками.
- **Касса** (`cash_shifts`, `cash_moves`): смена отвечает на вопрос «сколько
  в ящике», журнал — «сколько должен клиент». Наличные платежи смена берёт
  из `ledger` по `method='cash'`, копии не держит. Чья это смена, помнит
  сама запись журнала (`ledger.shift_id`, ставится по смене принявшего):
  точек две, смены на них открыты одновременно, и по одному окну времени
  платёж попадал в обе. Старые записи без отметки считаются по окну, но
  только когда вторая смена в ту же секунду не была открыта. Безнал смены
  не помнит: в карточке смены он по точке своей аренды (`db._ledger_rentals`);
  без точки у платежа или у смены - только когда смена была одна. В ящик
  он не идёт. Расхождение пишется как есть. Одна открытая смена на точку
  (частичный уникальный индекс).
- **Банк** (`bank_txns`): выписку Точки тянет процесс бота
  (`app/crm/banking.py` + `app/services/tochka.py`). Выписка заказывается
  один раз, а читается по своему номеру: банк собирает её не мгновенно, и
  круг, который каждый раз заказывает новую, не прочитает её никогда.
  Готовность берётся из статуса банка, а не из числа строк — за выходные
  операций может не быть вовсе. Строка не становится платежом сама —
  зачисляет оператор, и зачисление идёт обычным `payment` в `ledger`,
  одной транзакцией со сменой статуса строки. Автозачисление выключено по
  умолчанию и срабатывает только на номер договора нашего вида
  (`АВ-2026-000042`) у ровно одного клиента: номер, набранный в карточке
  руками, совпадает с номером велосипеда и датой - он лишь подсказка.
  Одни деньги - одно зачисление: автозачисление молчит при безнале той же
  суммы или ждущем «Я оплатил» за ±3 суток, «Я оплатил» при зачисленной
  строке выписки за те же сутки - только с галочкой «другой платёж».
- **Трекеры** (`crm.trackers`, `crm.tracker_positions`, `crm.tracker_alerts`):
  данные тянет опрос StarLine в процессе бота (`app/crm/tracking.py` +
  `app/services/starline.py`), панель в интернет не ходит. Тревога одна
  на вид на трекер (частичный уникальный индекс) и снимается сама, когда
  причина исчезла. Журнал позиций живёт месяц, чистится дневным проходом.
  Единственная команда устройству - блокировка мотора (`tracker_commands`,
  `trackers.blocked`): панель кладёт команду в очередь, опрос относит её
  в StarLine (`set_param`, режим «антиограбление») в начале круга и
  пишет ответ. Блокировка у StarLine срабатывает после остановки
  велосипеда, не на ходу: мотор перестаёт тянуть, когда тот уже стоит, -
  поэтому кнопка безопасна для курьера, а задержка до круга опроса не
  важна. Одна команда в очереди на трекер (частичный уникальный индекс).
  Привязка к велосипеду - на карточке трекера, не в списке: весь парк
  выпадающим списком в каждой строке весил 2 МБ на 130 трекерах.
- **Тревога - задача** (`tracker_alerts.level/state`): уровень срочный
  или жёлтый, состояние - новая, в работе, отложена, «это норма».
  «Это норма» НЕ закрывает тревогу: открытая не поднимется второй раз
  (тот же уникальный индекс), а исчезнет причина - опрос закроет её сам.
  Заглушек с сроком поэтому не нужно. `trackers.moved_at` - когда трекер
  последний раз ехал: по нему тревога «не двигается при аренде».
- **Справочники** (`crm.locations`, `crm.bike_models`, `crm.battery_models`,
  `crm.compat`): город - уровень над точкой, и своего часового пояса
  у него нет намеренно: вся система живёт в Europe/Moscow.
  Точки выдачи (с телефоном, режимом и координатами),
  каталог моделей с характеристиками и матрица совместимости.
  Модель в `crm.bikes` остаётся текстом — каталог связывается по названию,
  переезд на ссылки переписал бы живую историю парка.
- **Точки** (`crm.locations`, `crm.bike_location_log`): ключ точки -
  текст `locations.name`, как у парка, батарей и касс; `null` - «без
  точки». На id не переезжаем по той же причине, что модели, поэтому
  переименование - каскад одной транзакцией (`db.rename_location`), вместе
  с `?location=` сохранённых фильтров; имя, занятое записями вне
  справочника, не принимается - склейка с ними необратима.
  История места - свой журнал с триггером `crm.log_bike_location`, а не
  колонка и не строки в `bike_status_log`: там строка - смена статуса,
  и переезд сбросил бы «сколько стоит». `rentals.location` - снимок
  точки выдачи, замена его не меняет (и аренде без точки не дописывает:
  прошлые платежи уехали бы на чужую точку). В аренде велосипед стоит на
  точке аренды, «не на точке» включительно: выдача, возврат и замена
  ставят место тем же UPDATE, что и статус, а карточка - условием в самом
  UPDATE (`keep_rented_location`), иначе дни в аренде и платежи точки
  считали бы разные велосипеды. Запись `ledger` - точке своей аренды по правилу окупаемости
  (`db._ledger_rentals`), долг клиента - целиком точке его последней
  аренды. Строка «без точки» обязательна: сумма по точкам - общие три числа.
  Часы в текстах бота - из справочника (`points.hours_note`): точки аренды
  или заявки, иначе всех открытых; сдача «на любой точке» - всех открытых;
  зашитые 10–19 - только без справочника.
- **Переброска между точками** (`logic.transfer_plan`): подсказка на
  завтра и послезавтра, не автоматика. Спрос - выдачи модели на точке в
  тот же день недели за 8 недель плюс открытые заявки; предложение -
  свободные (без ремонта, брони, подменных) плюс `freeing_soon`. Точка
  отдаёт только сверх своего прогноза и запаса (`transfer_safety`).
  Перевозит оператор галочками: `update_bike(keep_rented_location=True,
  from_location=...)` - точка отправления из формы стоит в WHERE, и
  устаревшая форма не «везёт» велосипед с третьей точки; журнал мест
  пишет триггер, «сколько стоит» не сбрасывается.
- **Доп. аккумулятор** (`rental_extras`): цена периода у аренды одна -
  она начисляется и она же формирует средний чек; позиции только её
  расшифровывают. Цена велосипеда на выдаче лежит отдельно
  (`rentals.base_price`), иначе снятие позиции переоценило бы аренду по
  сегодняшнему тарифу. Тариф на аккумулятор - свой вид (`tariffs.kind`);
  нет цены на срок аренды - доп. аккумулятор не выдаётся вовсе, потому
  что бесплатная батарея и батарея без цены выглядят одинаково. Правка
  цены действует со следующего начисления: начисленное задним числом
  не переписывается. Кнопка «+ второй аккумулятор» в кабинете (пополнение,
  «продлю») - просьба команде, а не покупка: денег и позиции нет,
  позицию добавляет человек на точке (`rentals.battery_asked_at`, её же
  снимает позиция). Цена в кнопке - как у выдачи, по свободным
  подходящим батареям: тариф модели главнее запасного, разные - «от».
- **Заводское название модели** (`bike_models.factory_title`): в парке
  модель названа по накладной, в тарифах - по-клиентски. Каталог держит
  оба имени и связывает их (`logic.model_aliases`); переименовывать парк
  нельзя - на него ссылается закрытая история. Новое название модели
  (`db.rename_bike_model`) идёт каскадом в цены, заявки и акции, а старое
  становится заводским; удалить можно только модель без парка, цен,
  заявок и акций - иначе архив. Сид каталога - один раз
  (`bike_models_seeded`), поставочные имена без «(Два АКБ)» и «Monster» -
  разовой правкой `catalog_titles_v2`.
- **Удаление велосипеда** (`db.delete_bike`): только заведённого по
  ошибке - без аренд, ремонта, батарей, трекера, пересчёта, и пока он «на
  сборке» или заведён не больше `BIKE_DELETE_DAYS` назад; журналы
  триггеров уходят с ним. Стоявший в парке - только списание: его дни
  сидят в прошлых трёх числах.
- **Правка срока аренды** (`db.change_rental_term`, `rental_changes`):
  начало и следующее начисление. Вперёд - дни без списания, назад - не
  ниже начисленного периода (иначе двойное начисление); деньги не
  пишутся, причина обязательна, правка - строкой журнала.
- **Цена зависит от модели** (`tariffs.model`): тариф без модели —
  запасной, он работает, пока у модели нет своей цены. Одна цена на
  связку «модель + срок» среди действующих (частичный уникальный индекс).
  Выдача берёт тариф того же срока у выбранной модели (`match_tariff`),
  а не оставляет чужую цену. Каталог и цены владельца приезжают со схемой
  через `on conflict do nothing` — правки в панели важнее сида.

- **Входящие** (`inbox_threads`, `inbox_messages`, `app/crm/inbox.py`):
  обращения из Telegram, MAX, Авито и WhatsApp одной лентой, раздел
  `inbox` - только владельцу. Обращение - это разговор, а не заявка и
  не клиент: `bookings` и карточку оно не создаёт, в `ledger` не пишет.
  Текст шифруется отдельным ключом `INBOX_KEY` и живёт 90 дней; фото и
  файлы не хранятся. Ответ из панели - строка очереди, отправляет
  процесс бота (Telegram, MAX, Авито, WhatsApp через Wazzup); зависшее
  «отправляется» само не повторяется, а через 10 минут становится «не
  ушло» - отправка не идемпотентна; повтор - та же строка, а не копия.
  WhatsApp: ответ уходит с того нашего номера, на который писал человек
  (`inbox_threads.ext_channel`), подписку хука ставит бот
  (`inbox.wazzup_once`) на `/hook/inbox/<токен>` - вебхук Wazzup по
  своему ключу приходит без заголовка; токен из адреса не пишется ни в
  журнал запросов, ни в базу. Без Wazzup (Green-API, n8n) - только
  входящие, в панели - «ответил вне панели». Обращение
  принадлежит своему источнику (`origin`): хук не пишет в чат, который
  завёл опрос Авито. Карточку, выбранную руками (`client_manual`),
  автопривязка по телефону не трогает. Авито опрашивает бот
  (`app/services/avito.py`): первый удачный круг берёт только сутки, и
  старше срока хранения опрос ничего не возвращает. Хук `/hook/inbox`
  в `PUBLIC`: без токена его нет (404), принимает только `wa`, `avito` и
  `tgp` (личный Telegram-аккаунт через Wazzup - отдельный канал) -
  Telegram бота и MAX пишет сам бот, и подделать их через хук нельзя.
  Wazzup отвечает в WhatsApp, `tgp` и Авито с канала, через который
  писал человек (`ext_channel`, вид канала - `kind` в `wazzup_state`). Сигнал
  в чат - когда человек начинает ждать, без имени, телефона и текста:
  чат читают все, раздел - только владелец.

- **Франчайзи и роялти** (`franchisees`, `franchise_snapshots`,
  `franchise_months`, `app/crm/franchise.py`): у каждого франчайзи своя
  копия системы; наружу она отдаёт только агрегаты - `GET /hook/metrics`
  по токену `secrets/metrics_token` (пусто и в демо - 404): парк, три
  числа, выручку по месяцам, названия точек, без клиентов. Франчайзер
  забирает их процессом бота раз в сутки, панель - только кнопкой
  «Обновить сейчас». Токен франчайзи в базе - шифром ключа `secrets/franchise_key`.
  Чужой ответ - чужая строка (`logic.parse_metrics`: https, предел байт,
  типы и пределы чисел, чистка имён), а простой и чек пересчитываются из
  дней и выручки той же формулой: определение трёх чисел у сети одно.
  Роялти = выручка × % + фикс, Decimal; условия пишутся на месяц, пока он
  идёт - правка не переписывает прошлые, кроме явного «Условия с месяца»
  (опечатка после первого опроса). Прошлый месяц, который последний ответ
  застал незакончившимся (`franchise_months.partial`), - «неполные
  данные», а не готовый счёт. В `ledger` роялти не идёт.
  Раздел `franchise` - только владельцу.

- **Рабочая группа точек** (`ops_reports`, `app/crm/opsgroup.py`): бот
  читает темы группы (`OPS_CHAT_ID`, `OPS_TOPIC_*`) и сверяет формы с
  базой, 👍/👎 реакцией. Группа ничего не пишет в `ledger` и не создаёт
  аренд - это проверка, а не вход; единственное действие - «ЗАМЕНА»,
  тем же `swap_bike` и только оператором или сотрудником с правом на
  аренды. Стоп-лист - карточки со статусом, не список в коде. Адресов и
  телефонов из формы журнал не хранит: анкета зашифрована. В номере
  рамы и мотора кириллица-двойник читается латиницей, а B и V - одно
  (`logic.vin_key`, в SQL - `db._vin_sql`): «60В» с телефона - это вольты.

Статусы велосипеда: `new` (на сборке), `available`, `rented`, `repair`,
`maintenance`, `reserved`, `lost`, `sold`, `written_off`. `rented` ставит
и снимает только аренда, `new` снимает только ввод в эксплуатацию.
У батареи те же правила: `new`, `available`, `rented`, `repair`,
`maintenance`, `lost`, `written_off`, `sold`.

## 5. Правила работы над кодом

- Схема — только через `schema.sql`: он идемпотентен (`if not exists`,
  `add column if not exists`, `create or replace`) и применяется при старте
  под консультативной блокировкой. Отдельных нумерованных миграций нет —
  это осознанно, файл один и его читают сверху вниз. Выполняется только
  изменившийся текст (отпечаток - `crm.settings.schema_sha256`): прогон
  того же файла брал AccessExclusive на горячих таблицах и ловил deadlock
  с живыми запросами. Ожидание замка - `lock_timeout` с повторами, а не
  вечный старт.
- Суммы — `numeric(12,2)`, никаких float. В копейки не переводить: тип
  точный, а переезд тронул бы весь журнал ради формальности.
- Даты — `timestamptz`; `TZ` контейнеров и сессии Postgres — Europe/Moscow,
  панель показывает местное время. Пояс сессии - параметром подключения
  (`server_settings`), не `SET`: пул делает `RESET ALL` при возврате.
- Каждая денежная операция — запись в `ledger`, без «пересчитаю потом».
- Персональные данные: анкета в базе зашифрована ключом `secrets/pdn_key`,
  сканы на диске с удалением по сроку; модератор сверяет фото глазами.
  Переписка «Входящих» - своим ключом `secrets/inbox_key`, 90 дней.
  Распознавание текста страницы (OCR кириллицы) убрано за ложные
  срабатывания и не возвращается. Читается только машиночитаемая зона
  (`app/services/mrz.py` + `ocr.py`, tesseract в том же контейнере): она
  самопроверяемая по контрольным цифрам ICAO 9303, поэтому непрочитанное
  поле просто не показывается. Результат — одна строка на карточке
  модератора, ничего не решает и в базу не пишется. Читаются три раскладки:
  внутренний паспорт РФ, загранпаспорт любой страны и карта (ВНЖ, РВП,
  удостоверение).
- Анкета ветвится на гражданстве (`logic.anketa_steps`): у паспорта РФ
  код подразделения, у иностранного документа — срок действия. Пустое
  гражданство читается как «Россия», чтобы старые анкеты остались полными.
- Перед правкой прода — дамп. Тесты обязательны для денег, периодов,
  простоя, амортизации, триггера статусов; остальное — по мере сил.
  Полный прогон: `python3 -m unittest discover -s tests -q`; линтер `ruff check .`;
  списки файлов для деплоя проверяет `python3 consistency.py`.
- Коммиты на русском. Все новые файлы — в списки `deploy.ps1`.

## 6. Что не делаем здесь

- Продажи велосипедов (розница/опт/B2B) — amoCRM. Красная линия:
  **арендатор живёт здесь, покупатель — в amoCRM.** Проданный велосипед
  остаётся в парке со статусом `sold`, покупатель клиентом не становится.
- Телефония — контур n8n; маркетплейсы кроме Авито тоже. Сообщения
  Авито и WhatsApp приходят во «Входящие» (WhatsApp — шлюзом через хук,
  ответ из панели — через Wazzup).
  Рассылки клиентам переехали
  внутрь: шаблон, аудитория и отправка в Telegram и MAX — раздел «Рассылки». Банк переехал внутрь: выписка
  Точки разбирается в разделе «Касса», чек 54-ФЗ пробивает её эквайринг.
- Бухгалтерия, патент, НДС — 1С и банк. Здесь только выписка и чек.
